Complaint Triage an AI first pass for medical-device complaints

A pipeline on Azure that reads each incoming complaint, investigates it with tools, checks its own work, and hands a person a drafted, cited record to approve or edit, instead of a blank page. Every run also writes its own test evidence, so changes ship faster without skipping the paperwork. Built only on public FDA data. The AI proposes; a person decides.

See how it worksThe plan

The problem

Medical-device makers must review every complaint they receive. Was anyone hurt? Is it serious? Must the FDA be told? Then each answer has to be written up: what happened, what was checked, and why. It's careful, repetitive work, and much of it is documentation. A good first pass saves reviewers time without taking the decision away from them.

A first pass, not a decision

The system reads, investigates and suggests. A person approves or edits every case. Nothing is closed without a human.

A drafted record, with sources

Each suggestion comes as a draft write-up: what happened, what was checked, the decision and why, every claim linked to its source. A separate check confirms each source says what's claimed. The reviewer edits instead of writing from scratch.

Measured, not demoed

A test set I label myself, a baseline, and a gate that blocks any change that makes the scores worse. Every number in the series will come from a report you can rerun.

How it works

The diagram at the top shows the path of one complaint: five steps joined by queues. Around them sit the parts every step shares, and the parts that measure and improve the system.

Shared by every step

  • One gateway for every AI callA small model first and a larger one when it's unsure, a fallback when a model fails, cached answers, and the cost and time of every call.
  • Tools behind an MCP serverRead-only tools the agent can call, and nothing in a report can grant it more.
  • Hybrid searchKeyword and meaning-based search combined, then reranked.

Measures and improves

  • Eval harnessScores every version against reports I've labelled myself.
  • A gate on every changeCI fails if the scores drop by more than normal run-to-run noise, or if cost or speed get worse.
  • Two loopsAn unattended overnight batch with a circuit breaker, and a nightly loop that proposes one improvement at a time as a pull request.

Design choices

A few rules the whole system follows, and the quality-process idea each one borrows from.

  • A person decidesThe AI only suggests. A person approves or corrects every case, and nothing is closed without them.Complaint handling
  • Fix the cause, not just the caseEach correction is traced to its cause (the prompt, the retrieval or a rule) and kept as a test case, so the same mistake can't quietly come back.CAPA
  • The AI changes only through reviewThe nightly loop proposes one change at a time, tested on data it has never seen, as a pull request with its results. I merge it or close it.Change control
  • Every suggestion can be tracedIt's stored with the model, the prompt version, the sources it cited, the verifier's result, the cost and the time taken.Traceability
  • Evidence comes out of the workEvery test run writes a dated report tied to the exact code, prompts and settings. Every AI change arrives as a pull request with its results. Every design choice has a short decision record. The paperwork is a by-product, not a separate chore.Objective evidence
  • Severity firstReports that mention death or serious injury go to the top of the review queue. A suggestion that can't be verified is escalated, never guessed.Risk-based
  • No answer without evidencePersonal details are removed before any model call. Text inside a report is data, never instructions, and attempts to trick the model are part of the test set.Risk controls
  • The model is software I didn't writeEach model version is pinned, tested before any change, and has a fallback.SOUP

How it's measured

No numbers yet. The first baseline comes with the first slice, and every number will be published with the report that produced it.

Extraction accuracy

Does the reader fill each field the way I would?

Agreement with my decisions

How often the suggestion matches my call, corrected for lucky guesses.

Sources that hold up

Does each cited source really support its claim? Claims with no evidence behind them: the target is zero.

Reviewer effort

How long a review takes, and how much of the draft record the reviewer had to change.

Escalation rate

How often the system says "I can't verify this". Too high, and it isn't saving anyone time.

Cost and time per report

What one complaint costs, and how long it takes, including the slow cases.

Honest notes

  • Public data only: openFDA adverse-event reports (replayed as incoming complaints), openFDA recalls and public FDA guidance. No company's internal data.
  • A public report is not proof that a device caused an event, and FDA removes personal and confidential details before publishing.
  • Every public report was, by definition, sent to the FDA, so "must the FDA be told?" has almost no "no" examples. I'll show that limit next to the numbers.
  • Not a medical device and not regulatory advice. It makes no real reporting decisions.
  • Runs on a hobby budget (under about $50 a month), so most of it scales to zero when idle.
  • The code is in a private repository for now and will be published with the series.
  • I use an AI coding assistant. The design decisions, reviews and measurements are mine.
