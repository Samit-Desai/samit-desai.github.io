Transcript

12 parts · every spoken word

Every example uses one made-up device: a motorized rehab device in which a PC app sends settings to controller firmware that drives a motor moving a patient's arm or leg. Every number, ID and version in the story is made up.

Which build was tested?. It's release day for the made-up rehab device. The test report says build 398 passed, but the build about to go out is 412. Which one was actually tested? This is Episode 3: build it right, and prove it.

The big picture. Here's the one-page picture from Episode 1. The quality system holds everything, and risk management runs through every step. This episode lifts out the development flow: building the software, and showing it was built right.

A plan sized to the class. It starts with a plan, sized to the software safety class. Every class needs requirements, code, system tests and a release record. Class B adds an architecture, unit verification and integration testing. Class C adds a detailed design for every unit. In this story, the app and firmware are class B, a made-up rating.

Sprints, with the evidence in done. IEC 62304 doesn't prescribe a life cycle model, and this team works in sprints. AAMI TIR45 describes how agile practices fit. I think sprints work best when "done" includes the evidence: a story isn't done until its code, tests, updated requirement, risk check and review are recorded.

Everything versioned. Configuration management gives each controlled item an ID and a version: the code, requirements, tests, libraries, even the build tools. Once an item is under control, it changes only through an approved change request. So the team can say exactly what went into any release, and rebuild it.

SOUP and the SBOM. The app uses an open-source library for PDF reports. In IEC 62304, that's SOUP, software of unknown provenance: off-the-shelf software not developed for this device, or software without adequate development records. The team lists it in the SOUP list and the SBOM, the software bill of materials, and watches it for newly known problems. In the US, a cyber device's premarket submission must include an SBOM.

Verified, at three levels. For class B, verification happens at three levels. Unit tests check each piece, integration tests check the parts together, and system tests check the whole software against its requirements. Every result names the exact build it ran on. The trace report is built from those results, linking each requirement to tests that passed on that build.

The release record. The software release record names the exact build and lists the known bugs it ships with, called residual anomalies, each checked for risk. The software, its items and documents are archived. Because every result names its build, the near-miss is caught here: the tests name 398, but the release names 412. So build 412 is tested before anything ships. In my view, a test result is evidence only for the build it names.

Build the evidence and documents as you go. In my experience, it's easier to build the evidence and documents as you go. A CI pipeline is one way to do it, though IEC 62304 doesn't require one. It builds each version, runs the tests and ties each result to that build. It regenerates the SBOM, checks the SOUP list, and flags newly known vulnerabilities for a person to assess. AI drafts from those facts, and a named person reviews and signs.

The tools are checked too. One key guardrail: tools that create quality records are validated for their intended use, in proportion to the risk. That's in ISO 13485, and FDA's Computer Software Assurance guidance describes a risk-based way to do it.

Into the field. The software ships. Months later, a report comes in from the field. That's where Episode 4 begins.
